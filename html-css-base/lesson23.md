## Предметная область: Event Manager API

Платформа для организации мероприятий. Организаторы создают события, участники на них регистрируются, событиям можно назначать теги. Ниже — сжатая схема API, которой достаточно для этой практики (полная версия — в вашей собственной реализации backend).

| Метод | Путь | Назначение | Тело запроса | Ключевые поля ответа |
|---|---|---|---|---|
| `GET` | `/tags` | Список всех тегов | — | `{ id, name }[]` |
| `GET` | `/events` | Список событий, с фильтрами | — | `{ id, title, event_date, status, organizer_username, tags }[]` |
| `GET` | `/events/{id}` | Одно событие целиком | — | + `description`, `organizer_id` |
| `POST` | `/events` | Создать событие | `{ title, description, event_date, status, organizer_id, tag_ids }` | созданное событие целиком |
| `PUT` | `/events/{id}/status` | Изменить статус события | `{ status }` | событие с обновлённым статусом |
| `GET` | `/events/{id}/registrations` | Список регистраций на событие | — | `{ id, user_id, username, registered_at, status }[]` |
| `POST` | `/events/{id}/registrations` | Зарегистрироваться на событие | `{ user_id }` | созданная регистрация |

`GET /events` принимает необязательные query-параметры: `status`, `tag`, `organizer_id` — именно так реализована фильтрация на сервере.

Допустимые значения `status` события: `planned`, `ongoing`, `finished`, `cancelled`. Регистрация на событие со статусом `finished`/`cancelled`, а также повторная регистрация одного пользователя — запрещены бизнес-правилами сервера и возвращают `400` с телом `{ error: true, code: 400, message: "..." }`.

## Часть 1. Техническое задание

### Описание задачи

Нужно построить одностраничный фронтенд, который:

1. Загружает и показывает список событий с сервера, с возможностью отфильтровать список по статусу и/или тегу без перезагрузки страницы.
2. Даёт форму создания нового события — с выбором тегов из уже существующих на сервере.
3. Позволяет посмотреть список зарегистрированных участников конкретного события и зарегистрировать на него нового пользователя.
4. Позволяет отменить событие (сменить его статус на `cancelled`) прямо из карточки, без перехода на отдельную страницу.
5. Показывает пользователю понятные сообщения об ошибках — как сетевых, так и тех, что вернул сервер (в том числе нарушение бизнес-правил).

### Бизнес-правила фронтенда

1. Список событий подтягивается с сервера при загрузке страницы и отображается карточками — без единого события, зашитого напрямую в HTML.
2. Фильтрация по статусу и тегу выполняется через повторный запрос к `GET /events` с query-параметрами — не через скрытие/показ уже загруженных карточек на клиенте.
3. Форма создания события собирает `tag_ids` из отмеченных чекбоксов, а не из текстового поля со свободным вводом имён тегов.
4. После успешного создания события новая карточка появляется в списке немедленно, без повторной загрузки всего списка с сервера.
5. Кнопка отмены события должна быть видна только для событий, которые ещё не завершены и не отменены (`planned`/`ongoing`) — событие, уже отменённое или завершённое, отменить второй раз нельзя.
6. Список участников конкретного события загружается лениво — только при явном действии пользователя (например, клик «Показать участников»), а не для всех событий сразу при первой загрузке страницы.
7. Если сервер отклонил регистрацию из-за бизнес-правила (400 с содержательным `message` в теле ответа), пользователь должен увидеть именно этот текст, а не общую фразу «что-то пошло не так».
8. Интерфейс должен оставаться пригодным для использования на мобильном экране — минимум одна адаптивная перестройка раскладки.

### Требования к технологиям

| Требование | Детали |
|---|---|
| Разметка | Семантический HTML5 |
| Стили | Чистый CSS3: Flexbox и/или Grid, минимум один медиа-запрос, стилизованные состояния полей и кнопок |
| Логика | Чистый JavaScript (ES6+): `fetch`, `async`/`await`, работа с DOM через `querySelector`/`createElement`, без сторонних библиотек и фреймворков |
| Backend | Готовый Event Manager API, запущенный локально (`uvicorn main:app --reload`) |
| Запуск frontend | Live Server или `python3 -m http.server`, как в Уроке 22 — включая настройку CORS на стороне backend, если вы ещё не сделали этого раньше |

## Часть 2. Задание для реализации

### Структура проекта

```
event-manager-frontend/
├── index.html
├── style.css
└── script.js
```

### Разметка (HTML) — что должно быть

- `<header>` с заголовком приложения и формой фильтров (`<select>` для статуса, текстовое поле для тега, кнопка применения).
- `<main>`, внутри которого:
  - секция создания события: поля `title` (текст), `event_date` (`type="date"`), `organizer_id` (число), `description` (`textarea`), и место под чекбоксы тегов, которые подставит JS;
  - секция со списком событий — пустой контейнер, куда JS будет добавлять карточки, и строка статуса загрузки/ошибки.
- `<footer>` — произвольный, минимальный.
- Каждая карточка события (создаётся уже в JS, но спроектируйте её структуру заранее) должна содержать: название, дату, статус (визуально отличимый по цвету), организатора, список тегов, кнопку «Показать участников» и кнопку отмены события (условно видимую).

### Стилизация (CSS) — что должно быть

- Общий сброс отступов и `box-sizing: border-box`.
- Шапка и форма фильтров — через Flexbox.
- Сетка карточек событий — через CSS Grid, `repeat(auto-fill, minmax(...))`, чтобы число колонок само подстраивалось под ширину экрана.
- Хотя бы один медиа-запрос, меняющий раскладку под мобильный экран (mobile-first, как мы делали в Уроке 12).
- Стилизованные `input`/`textarea`/`select`/`button` с состояниями `:focus-visible` и `:invalid:not(:placeholder-shown)`, как в Уроках 13–14.
- Визуальное различие статусов события цветом (например, зелёный для `planned`, серый для `finished`, красный для `cancelled`).

### Взаимодействие с backend (JS) — что должно быть

- Функция загрузки и рендера списка событий, принимающая объект фильтров и строящая query-строку через `URLSearchParams`.
- Обработчик отправки формы фильтров, вызывающий загрузку списка заново с новыми параметрами (`event.preventDefault()` обязателен).
- Загрузка тегов при старте страницы и рендер их как чекбоксов в форме создания события.
- Обработчик отправки формы создания события: сбор данных (включая массив `tag_ids` из отмеченных чекбоксов), `POST /events`, добавление новой карточки в список при успехе, показ сообщения об ошибке при неудаче.
- Кнопка «Показать участников» на карточке — по клику лениво загружает `GET /events/{id}/registrations` и рендерит список; повторный клик не должен загружать данные заново, если они уже показаны.
- Мини-форма регистрации внутри раскрытого списка участников — `POST /events/{id}/registrations`, с обработкой и сетевых ошибок, и содержательных ошибок сервера (бизнес-правила).
- Кнопка отмены события — `PUT /events/{id}/status` с телом `{ status: 'cancelled' }`, с обновлением статуса прямо в существующей карточке без перезагрузки списка.
